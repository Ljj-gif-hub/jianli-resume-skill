# JD 定制分析（针对具体公司的 JD 生成简历）

目标：用户投某家公司时，把该公司的 **JD**（Job Description，职位描述）解析成一份"要求清单"，再对照项目真实证据定向——哪些技术/经历要放大、哪些要弱化、措辞怎么回扣 JD 关键词、公司业务怎么挂钩。**JD 的优先级高于 `positions.md` 岗位矩阵**（矩阵只用于判断岗位大类、选 1 主 1 辅画像）。

## 什么时候走 JD 模式

- 用户提供了具体公司的 JD：**粘贴 JD 文本** / **给 JD 文件路径**（先读文件）/ 口头描述对方要求
- 用户说"投 XX 公司"、"按这个 JD 来"、"帮我针对这家公司写"
- 多个公司：每家 JD 各生成一份简历，文件名 `简历-<公司>-<岗位>.md`

## JD 解析清单（逐项提取）

| 项 | 从 JD 哪里找 | 简历里怎么用 |
|---|---|---|
| 公司/业务背景 | JD 开头业务介绍、"我们做什么" | 项目定位、自我评价回扣公司业务方向 |
| 职位名称与层级 | 标题；实习/校招/社招暗示 | 确认岗位大类（映射岗位矩阵），标题对齐 |
| **硬性要求** | "任职要求/要求"里带 必须/熟练/精通/本科/3年+ | 简历必须正面响应的清单，逐条找证据 |
| 技术栈关键词 | JD 点名技术：Java/Spring Cloud/Redis/Kafka/Vue3/TS/LangChain/Agent/RAG... | 技能栏排序与项目 bullet 的主素材 |
| 职责项 | "岗位职责"里的动词（负责 XX 系统开发/优化/稳定性/性能） | 映射到项目里做过的同类事，逐条对应 |
| 加分项 | "优先/加分/熟悉以下更佳" | 有证据的顺手带一句，没有就不写 |
| 软性要求 | 团队协作/抗压/快速学习/ownership | 只在自我评价里自然体现，不堆空话 |

## 定向五步

1. **列硬性要求响应表**：JD 每条硬性要求 → 项目里 grep/文档找证据。
   - 有证据 → 写进简历对应位置
   - 没证据 → **明确不写**，并在交付说明的"JD 响应清单"里标注"未覆盖"（诚实，比硬凹强）
2. **技术栈交集/补集**：
   - **交集**（JD 要、项目有）→ 提到技能栏最前，写进项目 bullet
   - **补集**（JD 要、项目没有）→ 不写；用户确实了解可放"了解 X"并诚实标注，**绝不装作实战**
   - 同族技术可写"熟悉 X（项目用 Y）"桥接，但不能虚构 Y 不存在的能力
3. **关键词回扣**：JD 高频词（高并发/稳定性/用户增长/Agent 编排/性能优化...）自然分布到自我评价、项目 bullet、技能行——但每个词仍须项目内有证据支撑。
4. **职责映射**：把 JD 每一条"岗位职责"对应到简历某条亮点，或标注"该条暂未覆盖"。项目经历 bullet 的**排序**按 JD 职责优先级来，不是按时间线。
5. **弱化与删除**：JD 完全没提的领域压到一行"辅助扩展"或删掉，腾篇幅给 JD 关心的。

## 公司业务挂钩

- 项目一句话定位、自我评价，尽量贴合公司业务方向（如公司做电商 → 强调订单/支付/优惠券链路；做 AI 应用 → 强调 Agent/RAG/流式）。
- 只能基于**真实项目**挂钩，禁止为了贴合业务改项目描述。

## 多公司输出规则

- 同一项目、同一批真实证据，但**措辞/排序/强调每份不同**——这是 JD 定制的意义。
- 每份文件名：`简历-<公司>-<岗位>.md`，写入当前项目根目录或用户指定路径。
- 交付时给每份附"JD 响应清单"（JD 硬性要求 → 简历哪里对应 / 未覆盖），用户投递前一眼看出哪条没对上。
- 提醒用户：多份简历不要投错公司（尤其技术栈、公司业务相关的句子），投递前逐份核对。

## 冲突处理（真实性红线，永远优先）

- JD 要求 A、项目只有 B → 明确写 B 的实情，不伪造 A。
- JD 技术栈与项目差异大 → 直说项目侧重，不硬凹；必要时建议用户"这个岗位和你的经历匹配度低"。
- 自我评价/项目 bullet 的每个词仍须项目内可溯源（`references/project-analysis.md` 的指纹结果）。

## 交付内容

- `简历-<公司>-<岗位>.md` 主体
- 交付说明附 **JD 响应清单**：逐条列出 JD 硬性要求 → 简历对应位置（或"未覆盖"）
- 可选伴生产物同 SKILL.md（BOSS 文案/面试题/PDF），BOSS 文案也要回扣 JD 关键词
